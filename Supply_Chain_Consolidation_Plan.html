Recommendation — Supply Chain Systems Program

Nineteen systems, one supply chain: a consolidation roadmap

Your team's own data-structure audit surfaced 19 overlapping tools spanning PowerApps, SharePoint, Smartsheet, and Excel. This memo reads that audit back, names the cluster worth building first, and proposes a phased path that doesn't require replacing everything at once.

Source: Supply Chain Data Structure audit (Sheet1 / Process Map) Systems catalogued: 19 Status: Draft for review
01

What the audit actually shows

The spreadsheet you put together is more valuable than a typical systems list because it captures four things most audits skip: what platform each tool runs on, which systems share or duplicate data, who approves what, and — in the "Feedback on current functionality" column — what's actually broken, in your team's own words.

Read together, three findings stand out.

  • A tightly-coupled core already exists. The Process Map sheet draws it out: Material Request, Firm Zone, Ship Ticket, IRQ, and STO Request (Corporate) reference each other's records directly — a shipment on Ship Ticket can originate from a Material Request or a Firm Zone remake, and IRQ tracks the same delivery an STO created. These five aren't candidates for integration later; they're already one workflow, just split across a PowerApp, two SharePoint lists, and a standalone React app.
  • The platform itself is the bottleneck, not the people. "Clunky and buggy," "duplicate work," "today: N/A automation," "doesn't really have a tool" — these aren't complaints about process design, they're complaints about tools that can't do what the process needs. PowerApps and Smartsheet are form builders; none of them were built to run a multi-step approval with role-based routing, which is exactly what six of these nineteen rows are actually trying to do.
  • Some rows aren't systems at all — they're a gap with a name. Aging Inventory is listed with the note "doesn't really have a tool." Distressed inventory has no flag anywhere in the current landscape. These cost nothing to build wrong and everything to leave unbuilt, because right now they're nobody's job to maintain.

03

Why start with the core six, not everything

Nineteen systems can't move at once — not for budget reasons, for correctness reasons. Ship Ticket, IRQ, Material Request, Firm Zone, and Delivery Schedule already share overlapping records; migrating any one of them without the others just relocates the duplicate-entry problem instead of solving it. STO Request belongs in this same first phase for a different reason: it's the one system in the audit that already proves the architecture works — role-based approval routing, multi-site scoping, and an audit trail, running in production today.

Phase 1 is deliberately the smallest slice that removes a real duplicate-entry problem end to end, rather than the largest slice that looks impressive on a roadmap slide.

Working definition of "done" for Phase 1: a shipment can move from Material Request through Firm Zone, Ship Ticket, IRQ, and an STO record, touching each piece of data exactly once — no re-keying between systems, one audit trail end to end.
04

Proposed phasing

Phase 1 — Core movement platform Foundation build
STO Request Ship Ticket IRQ Material Request Firm Zone Delivery Schedule

One data model for "something needs to move" — request, approval, shipment, delivery, in a single database instead of five. This is the system of record the rest of the program builds on, so it gets the real engineering investment: proper auth and role/site scoping, a real audit trail, and a workflow engine that can express each of these five approval paths without a fresh PowerApp per exception.

Phase 2 — Attach the adjacent trackers Extend the platform
DNCM Vial Transfer Database SLED Aging Inventory (new)

Each of these already references Phase 1 data (Material Request, STO, SLED all overlap) but runs its own approval logic — non-conforming-material decisioning, cell-bank issuance sign-off, expiring-material review. Once the core platform exists, each is a new record type and workflow on the same foundation, not a new system. Aging Inventory is the one true green-field build in this phase: it has no existing tool to migrate, only a gap to fill.

Phase 3 — Satellite tools, case by case Evaluate individually
DSP Request Calibration Scheduling Cycle Count / Kitting Used Resin & TFF Label Tracker PSP Ship App

These touch the core workflow but don't block it — Calibration Scheduling and Label Tracker could plausibly become record types on the platform; Cycle Count and DSP Request may be better served staying on Smartsheet/PowerApps with a data sync back to the core rather than a full migration. Decide each on its own after Phase 1 ships and the pattern is proven, not up front.

06

Operating principles for the build

→
One workflow engine, many record types. Don't hand-build a bespoke approval flow per system the way the current PowerApps do. Model "request → review → approval → fulfillment" once, and let Ship Ticket, DNCM, and Vial Transfer each configure their own steps and roles against it.
→
Migrate data once, not per phase. Where two rows already share data today (IRQ / Delivery Schedule, Material Request / Firm Zone), bring both into the platform in the same phase, even if one is more urgent — otherwise the sync problem you're trying to kill just moves into the new system.
→
Keep Smartsheet/Excel where migration isn't worth it. Freezer Directory and the working Excel files don't need a rebuild — they need a clear owner and, if useful, a read-only feed into the platform. Not every row in the audit is a build.
→
Resolve eMDO before Phase 2 starts. It's the one system in the audit without a platform, UI, or clear owner listed, yet it feeds both DNCM and the SLED file. A short working session to scope it now is cheaper than discovering the gap mid-build.
