Overview

The STO Management System digitises the full lifecycle of pharmaceutical Stock Transfer Orders — from a Receiving Site submitting a material transfer request, through a multi-stage group approval workflow, to Receiving Site Logistics confirming final receipt and closing the order.

Core problem solved: Excel-based STOs had no audit trail, no real-time status visibility, and no role enforcement. This system enforces strict group-based field ownership at every step, logs every action immutably, and surfaces an actionable queue dashboard to each group so they know exactly what needs their attention.

Authentication & Group-Based Access

There is no login page. Instead, a Group Selector screen presents 6 group cards. Clicking a group issues a JWT that encodes the group, plant, and display name. Every subsequent API request sends this token in Authorization: Bearer <token>. The authenticate middleware verifies the signature and attaches the decoded payload to req.user.

AD-ready design: The JWT payload shape (userId, group, name, plant) already matches what an Active Directory LDAP / passport-azure-ad call will produce after mapping AD group names to the 6 group strings. Replacing the demo group array with an AD call requires no changes to middleware, routes, or frontend.

The 6 Groups

Receiving Site
Creates STO requests (DRAFT). Fills in all intake fields. Submits for planning review. Plant: Plant B.
Shipping Site Planning
Receives PLANNING_REVIEW queue. Fills MPN#, Batch#, Expiry Date. Approves (inventory confirmed) or Rejects. Plant: Plant A.
Shipping Site Logistics
Fills container info, freight cost, PGI date, estimated delivery date, actual ship date, tracking ID, ready-to-ship flag. Plant: Plant A.
Management / Finance
Management approves high-value STOs (auto-triggered). Finance gives final financial approval. Both record IGB Complete. Plant: ALL.
Receiving Site Logistics
Confirms receipt. Fills Actual Receipt Date. Closes out delivery (marks STO CLOSED). Plant: Plant B.
All Groups (read)
Every group can view all STOs regardless of status. Editing is strictly gated — only the active group at the current stage can write.

Management Approval Auto-trigger

When Shipping Logistics submits their fields, the backend computes management_approval_required from configurable thresholds stored in sto_config. The STO goes directly to FINANCE_REVIEW if management is not required.

const matThreshold    = parseFloat(process.env.MANAGEMENT_APPROVAL_MATERIAL_THRESHOLD || '10000');
const freightThreshold = parseFloat(process.env.MANAGEMENT_APPROVAL_FREIGHT_THRESHOLD  || '5000');
const mgmtRequired     = materialValue > matThreshold || freightCost > freightThreshold;
const newStatus        = mgmtRequired ? 'MANAGEMENT_REVIEW' : 'FINANCE_REVIEW';

Planning Approval Validation

Shipping Planning cannot approve without filling the mandatory fields. The backend validates this before writing:

if (approved && (!mpn_number || !batch_number || !expiration_date)) {
  res.status(400).json({ message: 'MPN Number, Batch Number and Expiration Date are required to approve' });
  return;
}

Audit Log

Every transition writes an append-only row to sto_audit_log. Nothing in the codebase deletes from this table. The log is shown in the STO detail view and powers the dashboard's Recent Activity feed via GET /api/sto/audit-log.

Safe Column Migrations

Three columns were added after the initial schema (inco_terms, estimated_delivery_date, igb_complete). Since SQLite's CREATE TABLE IF NOT EXISTS does not alter existing tables, the connection module runs safe migrations at startup:

for (const col of [
  'ALTER TABLE sto_requests ADD COLUMN inco_terms TEXT',
  'ALTER TABLE sto_requests ADD COLUMN estimated_delivery_date TEXT',
  'ALTER TABLE sto_requests ADD COLUMN igb_complete INTEGER DEFAULT 0',
]) {
  try { db.exec(col); } catch { /* column already exists — ignore */ }
}

Frontend API Client

// src/api/client.ts
const api = axios.create({ baseURL: 'http://localhost:4000/api' });

api.interceptors.request.use(cfg => {
  const token = localStorage.getItem('sto_token');
  if (token) cfg.headers.Authorization = `Bearer ${token}`;
  return cfg;
});

api.interceptors.response.use(r => r, err => {
  if (err.response?.status === 401) {
    localStorage.removeItem('sto_token');
    window.location.href = '/select-group';
  }
  return Promise.reject(err);
});

Key Design Decisions

1
No login page — group selector instead

The system is intended for internal use where identity will eventually come from Active Directory. Rather than building a placeholder login that will be ripped out, we implemented a group selector that issues the same JWT shape AD will produce. Swapping in an LDAP call requires no changes to middleware, routes, or frontend code.

2
MPN#, Batch#, Expiry Date owned by Shipping Planning — not Receiving Site

Per the process flow matrix, these fields are in the Shipping Planning (orange) row, not the Receiving Site (blue) row. The receiving site may not know the exact MPN or batch at request time — Shipping Planning verifies these during their inventory review. The creation form therefore omits them; the planning section of STODetail makes them mandatory before approval is allowed.

3
STO Number and Shipment ID owned by Receiving Site

Per the process flow matrix, these are in the blue (Receiving Site) row. The receiving site pre-fills them from their corporate systems when creating the request. Shipping Logistics does NOT write these — they were removed from the logistics form/endpoint.

4
Corporate STO Tracker Status owned by Receiving Site

Also in the blue row — it's entered at request creation time as a reference to the corporate tracker. It does NOT appear in the Receiving Logistics section (which has only Actual Receipt Date and Delivery Closed Out per the matrix).

5
Management approval computed server-side from thresholds

No group can set the management_approval_required flag — it's computed at logistics submission time from material_value and freight_cost against configurable thresholds. Thresholds live in sto_config and in .env, overridable without code changes.

6
better-sqlite3 named parameter requirement

SQLite via better-sqlite3 requires ALL named parameters present in the passed object, even if null/undefined. The seed script uses a DEFAULTS object and a normalize() function that spreads defaults before each insert to satisfy this requirement.

7
Audit-log endpoint must precede /:id route

GET /sto/audit-log is registered before GET /sto/:id in the Express router. If the order were reversed, Express would match the literal string audit-log as the :id parameter and the endpoint would never be reached.

8
Dashboard fetches independently, not Promise.all

The dashboard calls /sto and /sto/audit-log as separate fetches. If the audit-log fetch fails (e.g., before a backend restart picks up the new route), the STO data still loads and the activity feed silently stays empty — the whole page doesn't break.
