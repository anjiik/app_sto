Overview

The STO Management System digitises the full lifecycle of pharmaceutical Stock Transfer Orders — from a Receiving Site team submitting a material transfer request, through a multi-stage group approval workflow, to Receiving Site Logistics confirming final receipt and closing the order.

Core problem solved: Excel-based STOs had no audit trail, no real-time status visibility, and no role enforcement. This system enforces strict group-based field ownership at every step, logs every action immutably, and surfaces an actionable site-filtered queue to each team so they know exactly which STOs need their attention at their facility.

Authentication

The app supports two authentication modes, controlled by a single environment variable. The frontend login page is the same in both modes — only the backend behaviour changes.

Mode A — Demo / Development  PING_DEV_BYPASS=true

Login validates against a demo_users table in SQL Server. Passwords are bcrypt-hashed. A demo accounts panel appears on the login page listing all test accounts with one-click autofill. Run npm run seed to populate the demo users. Password for all demo accounts is Demo123!.

Mode B — Active Directory / LDAP  PING_DEV_BYPASS=false

Login validates against Active Directory via LDAP using the ldapts library. Users enter their AD username (e.g. john.doe or john.doe@company.com) and their Windows password. The demo accounts panel is hidden.

Two-step bind flow: The backend binds with a service account to search the directory for the user, then opens a separate LDAP connection to validate the user's password with their own credentials. The user's memberOf groups are mapped to an app role and site via ldapGroups.ts.

JWT Token

On successful login (either mode), the backend issues a signed JWT valid for 8 hours. The payload contains everything the frontend and API middleware need to enforce access:

{
  "userId": 0,           // 0 for AD users (no DB row), row ID for demo users
  "group":  "shipping_planning",  // one of 6 role keys
  "name":   "John Doe",          // displayName from AD or demo_users
  "site":   "XYZ"                // facility code — from AD group name prefix
}

AD Group → Role Mapping

Configured in backend/src/config/ldapGroups.ts. Each entry maps one AD group CN (common name) to a site code and an app role. Add a block of 6 entries per new site.

// backend/src/config/ldapGroups.ts
export const LDAP_GROUP_MAPPINGS = [
  // Site ABC
  { adGroup: 'ABC_STO_Receiving_Site',      site: 'ABC', appGroup: 'receiving_site' },
  { adGroup: 'ABC_STO_Shipping_Planning',   site: 'ABC', appGroup: 'shipping_planning' },
  { adGroup: 'ABC_STO_Shipping_Logistics',  site: 'ABC', appGroup: 'shipping_logistics' },
  { adGroup: 'ABC_STO_Management',          site: 'ABC', appGroup: 'management' },
  { adGroup: 'ABC_STO_Finance',             site: 'ABC', appGroup: 'finance' },
  { adGroup: 'ABC_STO_Receiving_Logistics', site: 'ABC', appGroup: 'receiving_logistics' },
  // Repeat for ABL, XYZ, etc.
];

Finding your AD group names: Set PING_DEV_BYPASS=false and attempt a login. If the user's groups don't match any entry, the error message lists all found AD group CNs — use those exact strings in ldapGroups.ts.

Roles & Site-Based Access

The 6 Roles

Receiving Site
Creates and submits STO requests. Fills all intake fields including need-by date, material details, shipping conditions. Only role that can create a new STO or edit a DRAFT.
Shipping Site Planning
Reviews PLANNING_REVIEW queue. Verifies inventory. Fills MPN Number, Batch Number, Expiration Date. Approves (→ Logistics) or Rejects. All 3 fields mandatory to approve.
Shipping Site Logistics
Fills container info, freight cost, PGI date, estimated delivery date, actual ship date, tracking ID, ready-to-ship flag. Submission auto-routes to Management or Finance based on value thresholds.
Management
Only triggered when material value > $10,000 OR freight > $5,000. Approves or rejects with notes. Records IGB Complete. Sees STOs from ALL sites.
Finance
Final financial gate before shipment is confirmed. Approves or rejects with notes. Records IGB Complete. Sees STOs from ALL sites.
Receiving Site Logistics
Confirms receipt. Fills Actual Receipt Date. Closes out delivery (marks STO CLOSED). Queue filtered by receiving site.

Site-Based Queue Filtering

All STOs are visible to all users on the All STOs page. However, the My Action Queue on the Dashboard is filtered by both the user's role and their home site. This ensures each team only sees the work that belongs to their facility.

Management Approval Auto-Trigger

When Shipping Logistics submits, the backend computes whether Management approval is needed based on configurable thresholds from .env:

const matThreshold    = parseFloat(process.env.MANAGEMENT_APPROVAL_MATERIAL_THRESHOLD || '10000');
const freightThreshold = parseFloat(process.env.MANAGEMENT_APPROVAL_FREIGHT_THRESHOLD  || '5000');
const mgmtRequired     = materialValue > matThreshold || freightCost > freightThreshold;
const newStatus        = mgmtRequired ? 'MANAGEMENT_REVIEW' : 'FINANCE_REVIEW';

Planning Approval Validation

Shipping Planning cannot approve without all three mandatory fields:

if (approved && (!mpn_number || !batch_number || !expiration_date)) {
  res.status(400).json({ message: 'MPN Number, Batch Number and Expiration Date are required to approve' });
  return;
}

Audit Log

Every transition appends a row to sto_audit_log. The table is append-only — nothing in the codebase deletes from it. The log is shown in the STO detail view and powers the Dashboard's Recent Activity feed.

Database Design

Microsoft SQL Server with Windows Authentication. The msnodesqlv8 driver uses the logged-in Windows account — no SQL username or password is needed. The connection pool is lazily initialised on first use.

Windows Auth: The app connects as the Windows user running the Node.js process. The SQL Server must have that Windows account (or its domain group) added as a login with db_owner or appropriate permissions on sto_management.

Key Design Decisions

1
Windows Authentication for SQL Server — no SQL password

The app and SQL Server run on the same Windows machine. Using Windows Auth means no SQL credentials to manage, rotate, or accidentally commit. The msnodesqlv8 driver handles this transparently — just set trustedConnection: true.

2
ldapts for AD authentication — pure TypeScript, no native compilation

Other LDAP libraries require native binaries that fail to compile on some Windows environments. ldapts is pure TypeScript — it installs with a plain npm install on any machine. The two-step bind (service account searches, separate client validates password) follows AD best practice.

3
Site stored in JWT from AD group name

The user's home site is needed at login time to filter their Dashboard queue. Storing it in the JWT avoids a DB lookup on every request. The site comes from the AD group name prefix (e.g. ABC_STO_Receiving_Site → site: ABC) via ldapGroups.ts.

4
Site-based queue filtering in the frontend, not the API

The Dashboard fetches all STOs and filters the queue in-memory. This avoids adding site-aware query logic to an endpoint that must remain unrestricted for the All STOs page. The filter is a simple array filter applied after the fetch — cheap since total STO counts are manageable.

5
Management and Finance are cross-site

These approval roles are corporate-level — approvers may review STOs from any facility. Keeping them cross-site avoids needing separate management accounts per site and matches the actual business structure where a single management team covers all locations.

6
MPN#, Batch#, Expiry Date owned by Shipping Planning — not Receiving Site

Per the process flow matrix, the receiving site may not know the exact MPN or batch at request time — Shipping Planning verifies these during inventory review. Making all three mandatory before Planning can approve enforces the process rule server-side.

7
Management approval auto-computed from thresholds, not manually set

No group can set the management_approval_required flag. It is computed at logistics submission from material_value and freight_cost vs. configurable thresholds in .env. Changing thresholds requires only an env variable change, not a code deployment.

8
Analytics filters applied uniformly via buildFilters() helper

All 7 analytics endpoints share the same buildFilters(q) function that builds parameterised SQL WHERE conditions from the query string. This ensures consistent filter behaviour across every chart and the raw data table, and prevents SQL injection via named parameters.

9
Requestor info denormalized at STO creation time

requestor_name and requestor_email are copied from the JWT payload into the STO row when created. This means the STO record remains accurate even if the user's AD display name changes or they leave the company — the history is preserved as it was at creation time.
