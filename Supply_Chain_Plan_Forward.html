Plan forward — supply chain systems

Nineteen tools are running one supply chain. Let's build it one platform at a time.

Our own systems audit mapped every database, PowerApp, and spreadsheet the team depends on — and where they quietly duplicate each other. This is the path from there to a single platform, phased so we never stop shipping to rebuild.

01

The ask

→

Build one platform for the core shipment workflow first — not all 19 systems at once.

Material Request, Firm Zone, Ship Ticket, IRQ, Delivery Schedule, and STO Request already share the same records across five different tools. Give them one data model and one workflow engine, prove it on a real shipment, then extend it outward to the rest of the landscape in two further phases.

02

Why this, why now

Three things the audit made undeniable.

FINDING 01

The core is already one workflow

The process map shows it plainly: a shipment moves through five systems and re-enters its own data at every hop. That's not five workflows — it's one, wearing five different interfaces.

FINDING 02

The tools can't do the job

"Clunky and buggy." "Duplicate work." PowerApps and Smartsheet are form builders — six of our nineteen systems are actually trying to run multi-step approvals, which is a different job entirely.

FINDING 03

Some gaps have no owner

Aging Inventory: "doesn't really have a tool." Distressed inventory has no flag anywhere today. That's not a UX complaint — it's money we can't currently see.

03

The phased path

Each phase ships something real before the next one starts.

Phase 1 — Core movement platform Foundation
STO Request Ship Ticket IRQ Material Request Firm Zone Delivery Schedule

One data model for "something needs to move" — request, approval, shipment, delivery — replacing five overlapping tools with one system of record. This is where the real engineering investment goes: role/site-scoped auth, a full audit trail, and a workflow engine that expresses every approval path without a new PowerApp per exception.

Ships when: a shipment moves from Material Request to a closed STO touching each piece of data exactly once — no re-keying, one audit trail.
Phase 2 — Attach the adjacent trackers Extend
DNCM Vial Transfer Database SLED Aging Inventory · new

Each of these already overlaps Phase 1 data but runs its own approval logic. Once the core exists, each becomes a new record type on the same foundation — not a new system. Aging Inventory is the one green-field build: no tool to migrate, only a gap to close.

Ships when: non-conforming material, cell-bank issuance, and expiring-material review all run through the platform's own approval engine.
Phase 3 — Satellite tools, case by case Evaluate
DSP Request Calibration Scheduling Cycle Count / Kitting Used Resin & TFF Label Tracker PSP Ship App

These touch the core workflow but don't block it. Some likely become platform record types; others may be better left on Smartsheet with a data feed back in. We decide each on its own once the pattern from Phase 1 is proven — not before.

Ships when: each tool has an explicit decision — migrate, integrate, or keep as-is — instead of an open question.
04

Analytics come with the platform, not after it

The audit calls out metrics and dashboards as unmet needs across a dozen rows. This isn't a Phase 4 add-on — it's what a shared data model gives you automatically.

The STO Request system already proves the point: because every transfer lives in one place with one status history, the questions the audit's "Metrics/Dashboard" column keeps asking — are we on time, where do things get stuck, why do things get rejected — are just queries against data that's already there. Nobody built a separate reporting project; the reporting is the data model.

06

What could slow this down

Named up front so they're decisions, not surprises.

RiskWhat it means for the plan
eMDO has no clear owner It feeds both DNCM and the SLED file but has no platform or UI listed in the audit. Needs a short scoping session before Phase 2 starts, not mid-build.
Phase 1 scope creep Every one of the 19 rows has a plausible case for "fold this in too." Phase 1 stays at six systems — that discipline is what makes Phase 2 and 3 cheap instead of each becoming its own program.
Parallel migration, not staged Systems that already share data (IRQ / Delivery Schedule, Material Request / Firm Zone) must move together. Migrating one without the other just relocates the duplicate-entry problem.
