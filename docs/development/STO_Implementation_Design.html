Overview

The STO Management System digitises the full lifecycle of pharmaceutical Stock Transfer Orders — from any user submitting a material transfer request, through a multi-stage, role- and site-scoped approval workflow, to Receiving Site Logistics confirming final receipt and closing the order.

Core problem solved: Excel-based STOs had no audit trail, no real-time status visibility, and no role enforcement. This system enforces strict role- and site-based field ownership at every step, logs every action immutably, and surfaces an actionable site-filtered queue to each team so they know exactly which STOs need their attention at their facility.

Authentication

The app supports two authentication modes, controlled by a single environment variable. The frontend login page is the same in both modes — only the backend behaviour changes.

Mode A — Demo / Development  DEV_BYPASS=true

Login validates against a demo_users table in SQL Server. Passwords are bcrypt-hashed. A demo accounts panel appears on the login page listing all test accounts with one-click autofill. Run npm run seed to populate the demo users. Password for all demo accounts is Demo123!. This is intentionally also a valid production setting — it is never blocked or warned against, so demo/test access can stay available on a production server if desired (see Section 9).

Mode B — Active Directory / LDAP  DEV_BYPASS=false

Login validates against Active Directory via LDAP using the ldapts library. Users enter their AD username (e.g. john.doe or john.doe@company.com) and their Windows password. The demo accounts panel is hidden.

Two-step bind flow: The backend binds with a service account to search the directory for the user, then opens a separate LDAP connection to validate the user's password with their own credentials. The user's memberOf groups are mapped to one or more role+site grants via GROUP_MAP.

JWT Token

On successful login (either mode), the backend issues a signed JWT valid for 8 hours. The payload carries the user's entire permission set — every role+site pair they hold — not just a single group/site:

{
  "adUsername": "john.doe@company.com",
  "name":       "John Doe",
  "grants": [                        // every {role, site} the user holds — source of truth
    { "group": "shipping_planning", "site": "ABC" },
    { "group": "shipping_planning", "site": "ABL" }
  ],
  "group": "shipping_planning",       // derived "primary" role — display only, never used for authz
  "site":  "ABC",                      // derived primary site — display only
  "sites": ["ABC", "ABL"]              // derived union of all grant sites — display only
}

Because grants[] travels inside the token, the backend never re-queries the database on later requests — every request just decodes and verifies the signature. A user can hold multiple roles and/or multiple sites at once (e.g. shipping_logistics@ABC + receiving_logistics@ABC, or shipping_planning@ABC + shipping_planning@ABL).

AD Group → Role Mapping

Configured in GROUP_MAP, backend/src/lib/ldap.ts. Each entry maps one AD group CN (common name) to a site code and an app role. Groups follow the naming convention APP-{SITE}-STO_Management_{Role}, plus a single company-wide admin group — five entries per site, no per-site admin group, and no group for creating an STO (any authenticated user can create one).

// backend/src/lib/ldap.ts
const GROUP_MAP: Record<string, { group: Group; site: string }> = {
  // Company-wide admin (bypasses all per-site checks)
  'APP-STO_MANAGEMENT_ADMIN': { group: 'admin', site: 'ABC' },

  // Site ABC
  'APP-ABC-STO_Management_Planning':              { group: 'shipping_planning',    site: 'ABC' },
  'APP-ABC-STO_Management_Logistics':             { group: 'shipping_logistics',   site: 'ABC' },
  'APP-ABC-STO_Management_Logistics_Receiving':   { group: 'receiving_logistics',   site: 'ABC' },
  'APP-ABC-STO_Management_Management':            { group: 'management',           site: 'ABC' },
  'APP-ABC-STO_Management_Management_Receiving':  { group: 'receiving_management', site: 'ABC' },
  // Repeat for ABL, ABS, MBM
};

Finding your AD group names: Set DEV_BYPASS=false and attempt a login. If the user's groups don't match any entry, the backend logs [AD auth] diagnostics (visible via pm2 logs sto-backend) listing every found AD group CN and whether each matched — use those exact strings in GROUP_MAP.

Roles & Site-Based Access

The 6 Roles

There is no dedicated "requestor" role — any authenticated user, holding any role or none, can create and submit a new STO. The six roles below govern the workflow steps after that.

Shipping Site Planning
Reviews PLANNING_REVIEW queue. Verifies inventory. Fills MPN Number, Batch Number, Expiration Date. Approves (→ Logistics), Revises (→ back to Draft), or Rejects. All 3 fields mandatory to approve.
Shipping Site Logistics
Fills container info, freight cost, tracking ID. Submission checks 6 conditions (value, freight, freight/value ratio, cold-chain, non-standard Inco terms, controlled shipping) — if any is true, routes to Management; otherwise straight to Receiving Logistics. Also does the post-management "confirm pass": actual ship date, delivery date, PGI date, ready-to-ship, SAP STO#.
Management
Shipping-site sign-off, only when one of the 6 conditions above triggers it. Approves or rejects with notes. A distinct AD group from Receiving Management — holding one does not grant the other.
Receiving Management
Receiving-site sign-off — the second, separate management gate. Both shipping-site and receiving-site management must approve before the STO can proceed to shipment.
Receiving Logistics
Confirms receipt. Fills Actual Receipt Date. Closes out delivery (marks STO CLOSED). Queue filtered by receiving site.
Admin
Company-wide, not per-site — a single AD group. Reverts an STO back one step, or sends it back with a mandatory reason. Manages archiving of old closed/rejected records.

Site-Based Queue Filtering

The All STOs list is scoped to what the user is entitled to see; the Dashboard's per-role queues are additionally filtered by site — both are enforced server-side via query parameters on GET /api/sto, not filtered client-side after an unrestricted fetch. Each queue is scoped by the matching role and site together (the same grant), not as two independent checks.

Management Approval Auto-Trigger

When Shipping Logistics submits, the backend checks six conditions — if any is true, the STO routes to Management; otherwise it goes straight to Receiving Logistics:

const matThreshold    = parseFloat(process.env.MANAGEMENT_APPROVAL_MATERIAL_THRESHOLD || '100000');
const freightThreshold = parseFloat(process.env.MANAGEMENT_APPROVAL_FREIGHT_THRESHOLD  || '20000');
const isColdShipping    = ['Cold 2-8C', 'Cold below 0', 'Frozen'].includes(shippingConditions);
const freightToValueRatio = materialValue > 0 ? freightCost / materialValue : 0;
const isNonStandardInco  = incoTerms !== '' && !['FCA', 'DAP'].includes(incoTerms);
const isControlledShipping = Boolean(controlled_shipping_required);

const mgmtRequired =
  materialValue > matThreshold ||
  freightCost > freightThreshold ||
  isColdShipping ||
  freightToValueRatio > 0.3 ||
  isNonStandardInco ||
  isControlledShipping;

If required, the STO goes through both shipping-site Management and receiving-site Receiving Management (two distinct AD groups) before returning to Shipping Logistics for a confirm pass, then on to Receiving Logistics. mgmt_confirmed=1 after both approvals is what tells the confirm-pass submission to advance directly rather than loop back into management again.

Planning Approval Validation

Shipping Planning cannot approve without all three mandatory fields:

if (approved && (!mpn_number || !batch_number || !expiration_date)) {
  res.status(400).json({ message: 'MPN Number, Batch Number and Expiration Date are required to approve' });
  return;
}

Audit Log

Every transition appends a row to sto_audit_log. The table is append-only — nothing in the codebase deletes from it. The log is shown in the STO detail view and powers the Dashboard's Recent Activity feed.

Database Design

Microsoft SQL Server with Windows Authentication. The msnodesqlv8 driver uses the logged-in Windows account — no SQL username or password is needed. The connection pool is lazily initialised on first use.

Windows Auth: The app connects as the Windows user running the Node.js process. The SQL Server must have that Windows account (or its domain group) added as a login with db_owner or appropriate permissions on sto_management.

sto_attachments

Any signed-in user can attach a file (PDF, JPG, or PNG, up to 10MB) to an STO at any point in the workflow — a Certificate of Analysis or other supporting document. File bytes are stored directly in the row (VARBINARY(MAX)), FK'd to sto_requests.id. No role or status restriction on adding one.

demo_users — Dev / Demo Mode

Used only when DEV_BYPASS=true. Stores test accounts with bcrypt-hashed passwords, a legacy single group_key + site, and an optional grants column (semicolon-separated role@site pairs) for multi-role demo accounts. Populated by npm run seed. In production this table is only consulted if DEV_BYPASS is deliberately left true; otherwise login goes through AD.

sto_config — present but unused

Key-value table pre-seeded with management_approval_material_threshold (10000) and management_approval_freight_threshold (5000). The application does not read this table — the real, effective thresholds ($100,000 / $20,000 by default) come from MANAGEMENT_APPROVAL_MATERIAL_THRESHOLD / MANAGEMENT_APPROVAL_FREIGHT_THRESHOLD in .env, or the built-in code defaults if unset. Changing sto_config rows has no effect.

schema_migrations

A manual checklist table (not an automated runner) recording which migration files have been applied to a given server — one row per filename, with a timestamp. Lets an admin see at a glance what state a server is in via SELECT * FROM schema_migrations instead of inspecting sys.columns by hand.

Key Design Decisions

1
Windows Authentication for SQL Server — no SQL password

The app and SQL Server run on the same Windows domain. Using Windows Auth means no SQL credentials to manage, rotate, or accidentally commit. The msnodesqlv8 driver builds an explicit ODBC connection string with Trusted_Connection=yes — this must not be changed to SQL authentication.

2
ldapts for AD authentication — pure TypeScript, no native compilation

Other LDAP libraries require native binaries that fail to compile on some Windows environments. ldapts is pure TypeScript — it installs with a plain npm install on any machine. The two-step bind (service account searches, separate client validates password) follows AD best practice.

3
Every role+site grant carried in the JWT, not just one

A user can hold several roles and/or cover several sites at once. Rather than picking one "primary" role+site to store, the token carries the full grants[] array — every {role, site} pair the user holds, derived from ALL of their matched AD groups via GROUP_MAP in lib/ldap.ts. This avoids a DB lookup on every request, and lets a single login correctly authorize a multi-role, multi-site user everywhere in the app.

4
Site-based queue filtering enforced server-side, via query params

GET /api/sto accepts shipping_site/receiving_site filters (comma-separated for multi-site users) that the Dashboard passes based on the user's grants. This keeps the same endpoint usable for both the unrestricted All STOs list and the site-scoped per-role queues, without ever fetching more data than the client needs.

5
Management is per-site, split into two distinct roles

Unlike an earlier design where Management was a single cross-site approval role, the current model ties Management to specific sites via its own AD group per site, and splits it into shipping-side (management) and receiving-side (receiving_management) — two separate groups, so holding one does not grant the other. This matches the real requirement that both the sending and receiving facility sign off independently on a flagged shipment.

6
MPN#, Batch#, Expiry Date owned by Shipping Planning — not the requestor

The requestor may not know the exact MPN or batch at request time — Shipping Planning verifies these during inventory review. Making all three mandatory before Planning can approve enforces the process rule server-side.

7
Management approval auto-computed from six conditions, not manually set

No role can set the management_approval_required flag directly. It is computed at logistics submission from material value, freight cost, freight-to-value ratio, cold-chain shipping conditions, non-standard Inco terms, and controlled-shipping status — the dollar thresholds are configurable via .env, the other four conditions are fixed business rules. Changing a dollar threshold requires only an env variable change, not a code deployment.

8
Analytics filters applied uniformly via buildFilters() helper

All 10 analytics endpoints share the same buildFilters(q) function that builds parameterised SQL WHERE conditions from the query string. This ensures consistent filter behaviour across every chart and the raw data table, and prevents SQL injection via named parameters.

9
Requestor info denormalized at STO creation time

requestor_name and requestor_email are copied from the submitting user's identity into the STO row when created, rather than referencing a user table (there isn't one — app_users was removed). This means the STO record remains accurate even if the user's AD display name changes or they leave the company, and the app never needs to resolve a stale foreign key to render a historical record.

10
No admin/creation-scoped AD groups — creation needs no role, admin is company-wide only

Earlier designs gated STO creation behind a "receiving site" role and allowed a per-site admin tier. Both were removed: any authenticated user can create an STO regardless of role, and admin access exists as a single company-wide AD group rather than one per site — matching how the role is actually used in practice.
